## 一、交流目标

1. **对齐认知**：让研发理解完整的个人上下文系统框架，明确当前方案的位置
2. **评审改进**：基于框架对照，讨论研发方案的改进方向和优先级

## 二、先对齐：完整框架是什么

### 2.1 系统定位

**不是「长期记忆系统」，而是「跨设备个人上下文系统」**。

核心区别：
- 长期记忆 = 记住更多东西
- 上下文系统 = 把经历、知识、经验转化为**可理解、可控制、可复用、可分享、可执行**的上下文资产

### 2.2 三条转化主线

**主线一（经历线）**：Experience → Memory → Insight
我经历了什么 → 我记住什么 → 我理解了什么

**主线二（知识线）**：World Knowledge → Interest Knowledge → Context
世界发生什么 → 什么和我有关 → 如何影响我的任务

**主线三（经验线）**：Experience → Shared Experience / Skill
什么做法有效 → 能否分享 / 能否变成技能

### 2.3 Context Object 模型（8 种类型）

| 类型                  | 说明      | 例子                |
| ------------------- | ------- | ----------------- |
| Memory              | 私人记忆    | 我的偏好、关系、承诺        |
| Personal Insight    | 个人洞察    | 用户真正关心的是经历如何转化为资产 |
| Interest Knowledge  | 个性化兴趣知识 | AI 眼镜行业动态（与我相关的）  |
| Knowledge Reference | 知识引用    | 某篇论文的摘要+来源+时间戳    |
| Task Context        | 任务上下文   | 当前项目进展、卡点、下一步     |
| Shared Experience   | 共享经验    | 展会试戴体验（可分享给他人）    |
| Skill               | 可执行技能   | 竞品研究流程            |
| Relationship        | 关系上下文   | 和某人什么能提什么不能提      |

每个 Context Object 都带有治理元数据：来源、权限、置信度、时效、状态、证据链。

### 2.4 上下文编排层（Context Orchestration）

位于上下文资产层和 Agent 使用层之间，负责在具体场景下做 8 种决策：

1. 相关性判断 — 需要哪些上下文资产
2. 优先级排序 — 冲突时谁优先
3. 刷新判断 — 外部知识是否需要更新
4. 权限判断 — 这条信息允许被使用吗
5. 置信度判断 — 这条信息可靠吗
6. 场景适配 — 现在适合主动提醒吗
7. 冲突处理 — 新旧信息矛盾怎么办
8. 组合生成 — 把哪些资产组合成上下文包

### 2.5 横向贯穿机制

- Governance：每条资产的来源、权限、置信度、时效、状态
- Evidence：所有高阶结论必须能追溯到证据
- User Control：用户可查看、修改、确认、删除
- Agent Persona & Relationship：Agent 的角色定位 + 与用户的长期互动模型

## 三、再评审：研发方案的位置

### 3.1 研发方案本质上是什么

**一个对话记忆系统**，解决的是「Agent 如何记住对话中的事实并有效召回」。

技术实现上比 mem0/Honcho/SuperMemory 更丰富（多了实体图谱、关系图、Observation 归纳），但范围局限在对话层面。

### 3.2 研发方案做得好的地方

| 方面                | 说明                            |
| ----------------- | ----------------------------- |
| 四层检索              | BM25 + 向量 + 实体图谱 + 节点关系，召回质量高 |
| Narrative Fact 提炼 | 把对话结构化，不是简单存原文                |
| Observation 机制    | 跨事实归纳高阶理解，方向正确                |
| 同步/异步分离           | 写入同步保数据，关系图异步不阻塞              |
| fact_type 分离      | World Fact 和 Experience 分开检索  |

### 3.3 研发方案缺失的核心能力

**完全缺失（没有对应物）：**

| 缺失类型 | 影响 |
|---------|------|
| Task Context | Agent 不知道「你现在在做什么」 |
| Interest Knowledge | Agent 无法主动感知与你相关的世界变化 |
| Knowledge Reference | 引用外部来源时无法追溯 |
| Shared Experience | 经验无法分享给他人 |
| Skill | 重复任务无法自动化执行 |
| Relationship | 社交场景下不知道什么能说什么不能说 |
| Agent Persona | Agent 的角色定位影响注意力分配 |

**有但严重不足：**

| 现有能力 | 缺什么 |
|---------|--------|
| Observation | 没有置信度、用户确认、证据追溯 |
| Memory | 没有权限标注、没有按人/项目组织 |
| 治理 | 几乎没有 |

### 3.4 具体场景对比

| 内容类型 | 研发方案 | 完整框架 |
|---------|---------|---------|
| 用户关注 latency | World Fact | Memory |
| 用户讨论了 memory retain | Experience | Experience Fact |
| 用户偏爱简洁回复 | Observation | Personal Insight |
| 项目进度：Phase 2，卡在隐私方案 | 没有对应类型 | Task Context |
| AI 眼镜最新发布了一款产品 | 没有外部知识线 | Interest Knowledge |
| 竞品研究流程：收集对比总结 | 没有经验线 | Skill |
| 展会的真实试戴体验 | 没有共享经验 | Shared Experience |

## 四、讨论议题建议

### 议题 1：框架对齐

研发方案目前只实现了「经历线」的一部分。是否需要向完整框架扩展？还是保持对话记忆系统的定位？

**建议**：先明确系统边界。如果要做一个通用的上下文平台，就需要扩展；如果只是 Agent 对话记忆，当前方案已经不错，但需要补治理机制。

### 议题 2：最优先补什么

**建议优先级**：
1. 治理元数据（置信度、权限、证据追溯）— 没有这个，其他能力都有风险
2. Task Context — 让 Agent 知道「当前在做什么」是最直接的体验提升
3. Observation 增强（置信度标注 + 用户确认 + 失效回退）— 已有基础，补成本低

### 议题 3：Observation 机制怎么演进

**建议**：
- 保留 entity-bound 的设计（比 Hindsight 更结构化）
- 补失效回退（源事实变更时自动删除/重建 Observation）
- 补用户确认机制（重要 Insight 需要用户确认后才能作为事实使用）

### 议题 4：是否需要「做梦」机制

当前 consolidation 是被动触发（retain 驱动）。是否需要后台定期执行？

**建议**：需要。被动触发能处理即时模式，但跨会话趋势发现、entity 去重、置信度衰减需要定期维护。类比人脑的睡眠。

建议的混合策略：
- 每次 retain 后：consolidation（即时）
- 每天一次：Dream（后台定期）— 跨会话模式发现 + entity 去重 + 置信度衰减
- 每月一次：User Calibration（用户校准）— 整理画像、推送给用户确认、修正

### 议题 5：Context Orchestration 怎么做

当前 recall 只是「检索 → 分桶输出」。是否需要编排层？

**建议**：这是长期方向。短期可以在 recall 基础上加简单的相关性过滤和权限检查，长期再做完整的 8 决策编排。

## 六、一句话总结

研发方案是一个**好的对话记忆系统**，但完整框架定义的是一个**更大的上下文操作系统**。

明天交流的核心问题是：**我们要做哪个？**

如果做后者，研发方案是好的起点，但需要补上治理、Task Context、知识线、经验线、编排层等核心能力。
