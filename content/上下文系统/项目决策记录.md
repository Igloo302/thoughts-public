# 📝 项目决策记录

## 2026-05-10 方案对比与决策

### 背景
需要将 macOS 用户操作行为数据（Screenpipe + OpenChronicle）注入 Hindsight，实现多输入源长期记忆。数据在工作 Mac 上，Hindsight 运行在本机 Mac。

### 备选方案

| 方案 | 描述 | 优点 | 缺点 |
|------|------|------|------|
| **① 直接改 Hindsight** | 让 Hindsight 原生支持操作数据格式 | 最彻底 | 涉及 Hindsight 源码改造太深 |
| **② 文件中转** | 工作 Mac 写入文件，本机读取 | 简单 | 文件同步延迟、冲突风险 |
| **③ 本机也装 Screenpipe** | 在家办公时本机直接采集 | 架构简单 | 只覆盖在家场景 |
| **④ 直接 API 推送 ✅** | 工作 Mac 脚本推送到本机 Hindsight | 零数据损失、实时 | 依赖网络连通 |

### 决策：方案四（直接 API 推送）

**理由**:
1. 本机 Mac 永远在线（运行 Hermes + Hindsight）
2. 工作 Mac 开机时可通过局域网/ZeroTier 访问本机
3. 保留原始结构化数据（避免 JSON → 自然语言的「有损转换」）
4. 「content 给语义提取 + metadata 给无损存储」的折中设计

### 技术约束
- Hindsight 的 `content` 字段必须是 `StrictStr`，被直接喂给 LLM
- 因此不能直接用原始 JSON 作为 content
- 解决：自然语言 content（供 LLM 提取）+ 原始 metadata（供精确查询）
